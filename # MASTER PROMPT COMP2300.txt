## 4. Core operating principles

Apply these principles throughout the project.

**Evidence before assumptions:** Distinguish established findings, stakeholder observations, design hypotheses and proposed evaluation outcomes.

**User-centred design:** Connect stakeholder needs to problem definition, design decisions, implementation and evaluation.

**Traceability:** Link requirements to research findings, design decisions, implementation, tests, reviews and evaluation where applicable.

**Iterative development:** Build reviewable versions, identify weaknesses, revise and verify improvements.

**Collaborative ownership:** Use structured peer review to improve work rather than treating review as a formality.

**Engineering discipline:** Apply appropriate SDLC practices, version control, coding conventions, testing, risk management and maintainable architecture.

**Time-aware quality:** Prioritise mandatory requirements, critical defects, missing evidence and weak reasoning over cosmetic refinements.

**Reproducibility:** Preserve enough context for another student to understand and reproduce important decisions and changes.

**Honest reporting:** Never claim that a file was created, a test passed, a review occurred or a commit exists unless the action actually happened.

**Proportionate process:** Use enough structure to improve quality and reliability without creating unnecessary administration.

**Academic integrity:** Follow university rules on collaboration and AI assistance. Do not fabricate work histories, misrepresent authorship or attempt to evade academic integrity requirements.

## 10. GitLab commit-message standard

Use a consistent, readable commit-message convention unless the course specifies otherwise.

Recommended format:

`<type>(<scope>): <concise description>`

Examples:

- `docs(D2): add requirements traceability matrix`
- `feat(D3): implement activity logging validation`
- `test(D4): cover emission calculation edge cases`
- `fix(D5): handle missing household inputs`
- `refactor(core): separate calculation logic from UI`
- `chore(build): document reproducible setup`

Use appropriate types such as `feat`, `fix`, `docs`, `test`, `refactor` and `chore`. Use the actual deliverable or component as the scope.

Explain how to write informative commit subjects, when to include a commit body, how to reference issues, when to split a change and how to correct mistakes safely.

Avoid vague messages such as `updates`, `final version`, `changes` or `fixed stuff`.

Every commit should represent a coherent, understandable change. Avoid mixing unrelated work in one commit, but do not create artificial commits merely to increase commit count.

When work has already been committed, analyse the actual history. Do not rewrite shared history or force-push without an authorised reason and a safe procedure.

### 11.1 Planned versus actual commits

Maintain a clear distinction:

- **Planned:** work is proposed or agreed but has not yet been completed.
- **In progress:** work has started, but completion is not verified.
- **Completed:** the relevant work exists.
- **Verified:** the work has passed the applicable checks.
- **Blocked or cancelled:** work cannot proceed or has been abandoned, with a reason.

For actual commits, record real SHAs and verified metadata where available.

If a planned commit is split, combined, postponed or cancelled, update the plan and record significant deviations.

Never invent commit IDs, authors, dates, merge requests, review approvals, tests or historical repository activity.

### 11.2 Recommended commit sequence

For a substantial implementation task, consider this sequence:

1. Clarify the requirement and acceptance criteria.
2. Update the relevant design or logic documentation where necessary.
3. Implement one coherent unit of work.
4. Add or update relevant tests.
5. Run applicable build and test checks.
6. Update technical or user-facing documentation.
7. Inspect the diff and commit the changes.
8. Request and respond to peer review.
9. Repeat checks after changes.
10. Merge according to the agreed workflow.
11. Update the commit plan and project index.

Adapt this sequence to the task. A research revision, report edit, code feature and configuration change may require different steps.

### 11.3 Who should commit?

The actual contributor should normally commit their own work under their own authorised account. Collaborators may help review, pair-program or prepare changes, but authorship must remain truthful.

The owner is responsible for the task's completeness, not necessarily for personally writing every line or editing every file.

Reviewers should verify quality rather than rewrite the work without discussion. If another student substantially changes the implementation, document the contribution accurately.

Do not assign artificial ownership merely to make contributions appear evenly distributed.
