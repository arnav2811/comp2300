# Official COMP2300 requirements summary

**Authoritative source inspected:** `COMP2300_PG_Updated_12_10_26.pdf`, supplied
outside the Git repository, draft version dated 23 September 2026.

## Core rules

- The confirmed challenge is **Carbon Footprint Awareness and Reduction —
  India-Centric Challenge** (PDF pp. 195–234).
- Source code must be stored in UoS GitLab and the implementation must use Java
  and JavaFX (pp. 313–320).
- Seven group deliverables are required: D1 problem space, D2 conceptual design,
  D3 evaluation plan/architectural design/setup, D4–D6 increments, and D7
  evaluation report (pp. 356–362).
- Group meetings must occur at least weekly. Minutes must use the supplied
  template, record decisions and assign actions to named owners (pp. 1180–1216).
- Each deliverable report must include completed work, its component tasks,
  project-management techniques, tools/techniques, and product/process
  reflection (pp. 1217–1244).
- Weekly peer reviews are submitted through Blackboard and contribute to PRISM
  (pp. 1246–1290). The official PDF does not define PRISM as an expansion.
- Individual reflections are Markdown, no more than 200 words each, and must
  address actual contribution/effect, process and theory, improvement, and
  evaluation of previous changes (pp. 1393–1436).
- PDFs require a sensible font of at least 12 pt, A4 pages and margins of at
  least 1.5 cm (pp. 1485–1489). Citations must use ACM SIGCHI style and
  references must be included; footnotes cannot replace citations (pp. 1510–1526).
- If GenAI contributes to submitted work, `genai.txt` must name the tools and
  versions and explain their purposes (pp. 144–159).

## D2 acceptance criteria

The D2 brief and rubric (pp. 508–595) require:

1. Evidence of a wide ideation process.
2. Three distinct concepts, each addressing the challenge, with a defensible
   choice justified by suitability, feasibility and stakeholder needs.
3. Small user stories grouped by epic, stakeholder association, MoSCoW priority
   and acceptance criteria.
4. A low-fidelity prototype at an appropriate fidelity that is accessible,
   feasible with current technology and novel. The prototype must not rely on
   speculative machine learning and must do more than merely log/display data.
5. The general deliverable-report sections listed under Core rules.

## Later gates that constrain D2 decisions

- D3 evaluation must recruit another COMP2300 group, use a user-centred method,
  occur in a controlled lab setting and avoid sensitive personal data (pp. 596–631).
- D4–D6 applications must compile and run, meet acceptance criteria, document
  testing and retain project-management evidence (pp. 734–771, 852–881, 982–1011).
- D5 additionally requires boundary/partition tests, scenario tests, task-hours
  summary and a definition of done.
- D6 additionally requires a user guide and expanded automated tests.
- D7 requires actual summative evaluation data; planned/synthetic results cannot
  be presented as findings.
